# Upgrade the winnow skill bundle to 0.11.0

## What this changes
No attendee-facing change. The `quiram/winnow` skill bundle moves from v0.10.1 to v0.11.0: `apm.yml` pins the new tag, `apm.lock.yaml` records it, and `.claude/skills/` is redeployed to match what the lockfile lists (files the new bundle adds appear, files it drops are removed).

## Where
- `apm.yml` — `dependencies.apm`: `quiram/winnow#v0.10.1` becomes `#v0.11.0`.
- `apm.lock.yaml` — regenerated by `apm install` (installed apm is 0.35.0; the lock was written by 0.33.0, so its `apm_version` line and key order may change, which is accepted). Must end with `version: 0.11.0`, `resolved_ref: v0.11.0`, and `deployed_files` / `deployed_file_hashes` for the new bundle. Never hand-edit it.
- `.claude/skills/**` — whatever `apm install` deploys; delete any directory under `.claude/skills/` the new lockfile no longer lists. `apm_modules/` is gitignored and stays uncommitted.
- `tests/unit/winnow-pin.test.js` — line 9 `VERSION = '0.11.0'`; line 10 `OLD` becomes `['0', '10', '1'].join('.')` (built from parts so the test file does not itself contain the string it forbids). Runs under `npm test`; reads files only, so no lane, no database and no helpers from `tests/helpers.js`.
- Stray references: a grep for `0.10.1` outside `specs/`, `apm.lock.yaml` and `package-lock.json` finds only `apm.yml` and the test file. `package-lock.json:1462` (`@tybys/wasm-util ^0.10.1`) is an unrelated npm dependency and is already excluded by the test's skip list.
- If the new bundle's skills are named or documented elsewhere (README slash commands, `context/`), update those; the existing README test fails if a named skill is not deployed.

## How it will be proved
| Done when | Check | Layer |
| --- | --- | --- |
| `apm.yml` pins `#v0.11.0`; lockfile has `version: 0.11.0` and `resolved_ref: v0.11.0` | `winnow-pin.test.js` "apm.yml pins the winnow bundle and the lockfile records it" with `VERSION = '0.11.0'`; false on main, which pins 0.10.1 | unit |
| `.claude/skills/` holds exactly what the lockfile deploys | `winnow-pin.test.js` ".claude/skills holds exactly what the lockfile deploys": every listed file exists, no leftover directory. On main this passes against the old lock, so it only proves the redeploy after the lock changes (the red-check is the version row above) | unit |
| No reference to `0.10.1` outside `specs/` and the lockfile | `winnow-pin.test.js` "no reference to the previous pin" with `OLD = '0.10.1'`; false on main because `apm.yml` contains it. Done by walking the tree in the test, which already skips `specs/`, so the spec naming the version does not trip it | unit |
| `npm test` passes | `npm test` | unit + API |

## Decisions
- The second Done-when criterion (`.claude/skills/` matches the lockfile) already holds on main against the 0.10.1 lock. This build proves it against the regenerated 0.11.0 lock, via the same test, after `apm install` runs. Is that the intended reading?
- The user said to "update locally", so the build runs `apm install` here rather than copying files by hand, and accepts the lockfile churn from apm 0.35.0 versus 0.33.0 if there is any. OK?

## Out of scope
Any change to winnow's behaviour, to how the harness uses the skills, or to application code.
